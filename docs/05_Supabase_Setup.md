# Настройка Supabase для «Бункера»

Этот документ относится к первой серверной заготовке в рабочей ветке проекта.

## Что добавлено

- 14 последовательных миграций: схема, лобби, тестовые комнаты, игровой цикл, эффекты действий и передача управления.
- Серверные таблицы комнат, участников, сессий, публичного состояния, каталога, экземпляров карточек, голосов, событий, финальных отправок и квитанций команд.
- RLS для таблиц, доступ к игровому состоянию — через проверяемые RPC.
- Закрытая таблица card_catalog: обычные клиентские роли не получают прямой доступ к полному каталогу.
- Серверный цикл: раздача, раскрытие, таймер, голосование, исключение, кризисы и финальный этап.
- 16 карточек действий имеют одобренные обработчики; 14 остаются draft до уточнения исходных правил.
- Автоматическая передача технического управления при исключении ведущего и перехват после 90 секунд без heartbeat.
- Общий план финального этапа могут сохранять и завершать оставшиеся в игре участники.
- Клиентские RPC-обёртки находятся в src/services/onlineRooms.ts; локальный импортёр — scripts/import-cards-to-supabase.mjs.

## До первого запуска

1. Создай проект Supabase. Регион выбирай ближе к игрокам, учитывая реальные сетевые тесты и требования к данным.
2. В настройках Authentication включи Anonymous Sign-Ins.
3. Выполни SQL-миграции из папки `supabase/migrations` строго по порядку имён — от `202611040001` до `202611040014` — через Supabase SQL Editor либо Supabase CLI.
4. Если миграции 001–013 уже применены, выполни только `202611040014_short_room_invite_codes.sql`. Не запускай старые миграции повторно вручную.
5. Убедись, что каждая новая миграция завершилась без ошибок и появилась в истории миграций.
6. Выполни импорт каталога с локального компьютера владельца.

Для создания комнаты, подключения по коду, получения снимка и подготовки старта доступны RPC api_create_room, api_join_room, api_get_room_snapshot и api_start_game. Для выхода из лобби/архивной комнаты и закрытия ещё не начатой комнаты добавлены api_leave_room и api_close_room. Новые коды приглашения состоят из пяти заглавных букв (без `I` и `O`), поэтому их проще продиктовать или ввести с телефона. Старые 32-символьные шестнадцатеричные коды продолжают приниматься, чтобы не ломать уже созданные комнаты. В базе хранится только SHA-256 кода.

## Импорт 180 карточек

Скрипт читает локальный assets/manifest.json (путь можно переопределить через BUNKER_CARD_MANIFEST_PATH), проверяет 180 уникальных ID и ровно 30 карт в каждой из шести категорий, затем загружает данные в закрытую таблицу card_catalog. Для dry-run ключ Supabase не требуется.

PowerShell из корня проекта:

```powershell
npm run db:import-cards -- --dry-run

$env:SUPABASE_URL = "https://YOUR_PROJECT_ID.supabase.co"
$env:SUPABASE_SERVICE_ROLE_KEY = "YOUR_SERVICE_ROLE_KEY"
npm run db:import-cards
Remove-Item Env:SUPABASE_SERVICE_ROLE_KEY
Remove-Item Env:SUPABASE_URL
```

Для первого шага можно использовать --dry-run: он проверяет локальный манифест, не отправляя данные. Структурную проверку миграции без подключения к Supabase запускает `npm run db:validate-migration`; она проверяет число таблиц и RPC, наличие RLS, баланс SQL-блоков, invite hashing, короткий формат кода и отсутствие прямых grants роли anon.

**Ключ service_role является секретом.** Не добавляй его в .env.local, VITE_*, GitHub Actions, React-код или Git. Используй его только в локальном PowerShell-сеансе для импорта. Не отправляй ключ в переписке.

## Переменные frontend

Скопируй `.env.example` в `.env.local` и укажи только публичные параметры:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_ANON_OR_PUBLISHABLE_KEY
```

Публичный anon/publishable key можно использовать в браузере, потому что доступ ограничивается RLS и RPC. Никогда не указывай service_role key в переменной с префиксом VITE_.

## Текущее состояние реализации

- Онлайн-лобби, создание обычной/тестовой комнаты и вход по коду работают через RPC, если соответствующие миграции и каталог уже загружены в нужный Supabase-проект.
- В обычной комнате сервер требует 8–16 реальных участников. В тестовой комнате недостающие места до минимума можно заполнить ботами.
- После старта сервер хранит личные карты, публично раскрытые карты, активные кризисы, фазу, дедлайн брифинга, голоса и результат исключения.
- Тестовые боты автоматически раскрывают по одной карте в каждом раунде и голосуют случайно. Они предназначены для проверки технического цикла, а не для имитации разумных игроков.
- Realtime используется как сигнал перечитать серверный снимок. При переподключении клиент снова получает актуальное состояние.
- Heartbeat отправляется раз в 20 секунд. Если контролирующий участник не отвечает 90 секунд, живой участник может запросить передачу технического управления. Если ведущий исключён голосованием, управление автоматически переходит первому оставшемуся живому человеку.
- Финальный план сохраняется как одна общая запись. Любой оставшийся живой участник может обновить её и завершить партию после сохранения. Одновременное совместное редактирование с разрешением конфликтов пока не реализовано.
- Все 30 исходных карточек действий присутствуют в каталоге. 16 действий имеют одобренные серверные обработчики. 14 остаются в статусе draft до утверждения процедур.
- Safe Boot сохраняет технический флаг на раунд, но автоматическая система применения эффектов Уязвимостей ещё не реализована. Workaround помечает кризис, но автоматическая проверка финального плана пока не исключает его.
- Неоднозначные правила не автоматизируются: в частности, ничья обычного голосования возвращает ошибку `VOTE_TIE_NEEDS_RULE`, а не выбирает участника случайно.

## Приватность каталога

Таблица `card_catalog` закрыта для обычных ролей `anon/authenticated`, а RPC возвращает личные карты только владельцу и публичные карты после раскрытия. Но исходные описания всех 180 карточек по-прежнему лежат в публичном GitHub-репозитории в JSON-манифестах, документации и исходниках локального каталога. Кроме того, посетителям доступен каталог карточек в интерфейсе.

Поэтому закрытость таблицы Supabase защищает серверную раздачу и состояние комнаты, но **не делает сами тексты карточек секретными**. Нельзя использовать текущий публичный репозиторий как хранилище конфиденциального набора карточек. История Git тоже сохраняет ранее опубликованные версии файлов.

## Публикация на GitHub Pages

В репозитории добавлен workflow `.github/workflows/deploy-pages.yml`. После объединения изменений в `main` он автоматически:
1. Установит зависимости Node.js.
2. Соберёт production-версию командой `npm run build`.
3. Опубликует папку `dist` через GitHub Pages.

Перед первой публикацией открой GitHub: **Settings → Pages → Build and deployment → Source** и выбери **GitHub Actions**. После этого проверь вкладку **Actions** и дождись успешного workflow Deploy to GitHub Pages.

Публикация из текущей рабочей ветки не запускается автоматически: workflow предназначен для `main`, чтобы незавершённые изменения не заменили рабочий сайт. CI для Pull Request отдельно проверяет сборку.

## Проверки и границы проверки

- GitHub Actions проверяет исходный каталог (dry-run), структуру базовой миграции, обработчики действий, runtime-контракты, отсутствие service_role в frontend, TypeScript и production build.
- `npm run db:smoke` запускает опциональную проверку настоящего Supabase-проекта: анонимный вход, создание тест-комнаты, заполнение ботами, старт, пять личных карт, первый кризис, раскрытие карты и серверный таймер. Скрипт создаёт тестовую комнату и пытается закрыть её после проверки.
- Smoke-тест не заменяет полную многопользовательскую проверку, тест всех 5 раундов, проверку всех 16 действий, нагрузку на 25 одновременных посетителей или ручной тест адаптивности.
- Миграции в реальный проект Supabase нужно применять только после проверки URL проекта. Не запускай миграции в случайном проекте из списка подключённых аккаунтов.
- Неразрешённые вопросы Q-02, Q-04–Q-19, Q-21–Q-26 продолжают ограничивать автоматизацию некоторых игровых процедур. Точный перечень — в `docs/02_Game_System.md`.
