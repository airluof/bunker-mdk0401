# Настройка Supabase для «Бункера»

Этот документ относится к первой серверной заготовке в рабочей ветке проекта.

## Что добавлено

- SQL-миграция supabase/migrations/202611040001_initial_multiplayer_schema.sql.
- Серверные таблицы комнат, участников, сессий, публичного состояния, каталога, экземпляров карточек, голосов, событий, финальных отправок и квитанций команд.
- RLS для чтения данных комнаты только её действующими участниками.
- Закрытая таблица card_catalog: обычный клиент не получает к ней прямой доступ.
- RPC: api_create_room, api_join_room, api_get_room_snapshot и api_start_game.
- Клиентские обёртки в src/services/onlineRooms.ts.
- Локальный административный импортёр scripts/import-cards-to-supabase.mjs.

## До первого запуска

1. Создай проект Supabase. Регион выбирай ближе к игрокам, учитывая реальные сетевые тесты и требования к данным.
2. В настройках Authentication включи Anonymous Sign-Ins.
3. Выполни SQL-миграцию через Supabase SQL Editor либо Supabase CLI.
4. Убедись, что в SQL Editor миграция завершилась без ошибок.
5. Выполни импорт каталога с локального компьютера владельца.

Для создания комнаты, подключения по коду, получения снимка и запуска доступны RPC api_create_room, api_join_room, api_get_room_snapshot и api_start_game. Для выхода из лобби и закрытия ещё не начатой комнаты добавлены api_leave_room и api_close_room.

## Импорт 180 карточек

Скрипт читает локальный assets/manifest.json (путь можно переопределить через BUNKER_CARD_MANIFEST_PATH), проверяет 180 уникальных ID и ровно 30 карт в каждой из шести категорий, затем загружает данные в закрытую таблицу card_catalog. Для dry-run ключ Supabase не требуется.

PowerShell из корня проекта:

\`\`\`powershell
$env:SUPABASE_URL = "https://YOUR_PROJECT_ID.supabase.co"
$env:SUPABASE_SERVICE_ROLE_KEY = "YOUR_SERVICE_ROLE_KEY"
npm run db:import-cards -- --dry-run
npm run db:import-cards
Remove-Item Env:SUPABASE_SERVICE_ROLE_KEY
Remove-Item Env:SUPABASE_URL
\`\`\`

Для первого шага можно использовать --dry-run: он проверяет локальный манифест, не отправляя данные.

**Ключ service_role является секретом.** Не добавляй его в .env.local, VITE_*, GitHub Actions, React-код или Git. Используй его только в локальном PowerShell-сеансе для импорта. Не отправляй ключ в переписке.

## Переменные frontend

В локальном .env.local Vite-приложения нужны только публичные параметры:

\`\`\`dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_ANON_OR_PUBLISHABLE_KEY
\`\`\`

Публичный anon/publishable key можно использовать в браузере, потому что доступ ограничивается RLS и RPC. Никогда не указывай service_role key в переменной с префиксом VITE_.

## Ограничения текущей итерации

- Комнаты, вступление, снимок комнаты и первоначальная раздача на сервере подготовлены, но существующий интерфейс src/App.tsx ещё не переключён на эти вызовы.
- Серверный движок раскрытия карт, голосования, переходов фаз, эффектов действий и финального аудита пока не реализован.
- Условие старта сейчас задано как 8–16 активных участников (по текущему ограничению проекта).
- Процедуры, отмеченные как требующие утверждения в docs/02_Game_System.md, намеренно не автоматизированы.
- Realtime-подписки готовы на уровне клиента и публикации таблиц; обработка события должна после сигнала перечитать api_get_room_snapshot.
- До подключения реального проекта Supabase нельзя считать схему применённой или мультиплеер работоспособным.

## Важное ограничение приватности каталога

Таблица card_catalog закрыта для обычных ролей anon/authenticated. Однако текущий публичный репозиторий всё ещё содержит исходные JSON-манифесты с текстами 180 карточек, а существующий frontend импортирует assets/manifest.json. Поэтому на этом этапе нельзя заявлять, что содержимое скрытых карточек защищено от игроков. Следующий обязательный этап — перевести UI на серверные RPC, затем убрать манифесты из актуального публичного дерева. Уже опубликованная история Git может сохранять старые версии файлов; удаление текущей копии не отменит прошлую публикацию.
