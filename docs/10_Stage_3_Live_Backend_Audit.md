## 1. Миграции

Новые миграции не требуются.

## 2. Структура и RLS

Проверено 15 таблиц схемы `public` и одна таблица схемы `private`.

- RLS включён на всех 15 таблицах `public`.
- Прямые права `SELECT` для `anon` и `authenticated` на таблицы `public` не выданы.
- Для `rooms`, `room_members`, `game_sessions` и `public_game_state` определены политики чтения через `private.is_active_room_member(room_id)`.
- Функция `private.is_active_room_member` сверяет `auth.uid()` с активным участником этой комнаты.
- Остальные таблицы доступны игровому API через серверные RPC, а не прямое чтение клиентом.

Отсутствие RLS-политик у 11 таблиц `public` и таблицы `private` отмечается Advisor как информационная/предупреждающая находка. При текущей модели API-only это не означает, что нужно открывать прямой доступ. Не добавлять широкие политики и не выдавать прямые права только ради исчезновения предупреждения.

## 3. Серверные функции и Advisor

Проверены функции `SECURITY DEFINER`:

- у публичных RPC задан пустой `search_path`;
- прямой `EXECUTE` для роли `anon` не предоставлен;
- функции вызываются ролью `authenticated`, что ожидаемо для Supabase Anonymous Sign-Ins: анонимные сессии используют роль Postgres `authenticated`;
- публичные RPC проверяют пользователя через `auth.uid()`; функции `api_start_game` и `api_start_test_game` являются SQL-обёртками и передают выполнение `private.start_game_core`, где проверка пользователя выполняется.

Advisor показывает 27 предупреждений о доступности `SECURITY DEFINER` RPC для `authenticated`. Это общий сигнал для ручной проверки, а не основание массово отзывать `EXECUTE`: такие функции составляют серверный API игры. Изменять их права без аудита каждого вызова опасно.

## 4. Результаты Security и Performance Advisors

### Security

- 12 находок `RLS Enabled No Policy`: 11 таблиц `public` и одна таблица `private`. С учётом отсутствия прямых прав чтения это соответствует закрытому доступу через RPC; широкие политики не добавлялись.
- 27 находок `SECURITY DEFINER` для `authenticated`: требуют точечной проверки авторизации, но не массового отключения API.
- Предупреждения о доступе анонимных участников к четырём таблицам соответствуют режиму игры с anonymous sign-in и ограничению чтения членством в комнате.
- Включение защиты от скомпрометированных паролей отмечено как рекомендация Auth. Это отдельная настройка; в рамках аудита она не менялась.

### Performance

- 17 внешних ключей не имеют покрывающих индексов.
- 3 индекса Advisor считает неиспользуемыми.

Это задачи оптимизации, а не повод немедленно менять схему в живой базе. Перед добавлением/удалением индексов нужно проверить запросы, размер таблиц и нагрузку. Никакие индексы не менялись.

Health Advisor не вернул находок.

## 5. Проверка логики вскрытия

По текущим определениям функций в базе:

- `api_reveal_card` принимает любую закрытую карту владельца, не требует категорию `roles` в первом раунде;
- выбранная карта получает `pending_reveal`;
- снимок игрока возвращает его собственные карты отдельно от публичных раскрытых;
- при переходе `api_transition_game_phase(..., 'briefing', ...)` сервер переводит ожидающие карты в `revealed` и создаёт публичные события в рамках одной транзакции;
- игрок не может выбрать более одной карты за раунд благодаря записи в `game_round_reveals`.

Это проверка определений SQL и структуры данных. Она не заменяет проверку видимости из двух реальных клиентских сессий.

## 6. Активные тестовые комнаты

Во время read-only проверки в базе находились две активные тестовые комнаты. В каждой было 8 активных участников, из них 7 ботов; для каждого участника было выдано по пять карт. Проверены связи карточных записей с записями вскрытия — нарушенных ссылок и ожидающих карт без записи вскрытия не обнаружено.

Комнаты не создавались, не закрывались и не изменялись в рамках этого аудита. Состояние активных комнат может меняться, пока игроки продолжают тестирование.

## 7. Почему клиентский smoke-тест ещё не выполнен

Скрипт `npm run db:smoke` использует `@supabase/supabase-js`, выполняет `auth.signInAnonymously()`, затем создаёт отдельную тестовую комнату, добавляет ботов, запускает игру, выбирает карту и переводит фазу в брифинг.

Подключённый здесь Supabase-коннектор позволяет читать схему, историю миграций, выполнять SQL и запускать Advisors, но не предоставляет клиентскую анонимную Auth-сессию для этого скрипта. В локальной среде отсутствует пакет `@supabase/supabase-js`, а установка из npm registry не удалась из-за недоступности сети. Поэтому полноценный клиентский smoke-тест не объявляется успешным и не подменяется SQL-запросом с привилегиями администратора.

Важно: cleanup в текущем smoke-скрипте вызывает `api_exit_test_room`. Для ведущего эта функция архивирует тестовую комнату и завершает игровую сессию, но не удаляет созданные строки. После успешного запуска остаётся архивная QA-комната.

## 8. Что остаётся сделать

1. Выполнить `npm run db:smoke` из среды репозитория с URL целевого проекта и публичным `anon`/`publishable` ключом. Не использовать `service_role`.
2. Проверить два реальных браузера: выбор разных категорий, приватность до брифинга, одновременное раскрытие после перехода.
3. Проверить перезагрузку, переподключение Realtime и резервный опрос.
4. Пройти голосование, исключение, следующий раунд и финальный план.
5. Только после этого провести проверку 8–16 реальных игроков и нагрузочный тест на 25 одновременных посетителей.
